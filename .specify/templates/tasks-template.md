# 任务：[FEATURE NAME]

**输入**：来自 `/specs/[###-feature-name]/` 的设计文档

**前置条件**：plan.md（必需）、spec.md（用户故事必需）、research.md、data-model.md、contracts/

**测试**：当公开路由、上游中转行为、认证边界、错误映射或流式行为发生变化时，网关边界测试是必需的。其他测试仅在不影响宪章要求的网关验证时才可视为可选。

**组织方式**：任务按用户故事分组，确保每个故事都可以独立实现和测试。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**：可并行执行（不同文件、无依赖）
- **[Story]**：任务所属用户故事（例如 US1、US2、US3）
- 描述中必须包含准确文件路径

## 路径约定

- **单项目**：仓库根目录下的 `src/`、`tests/`
- **Web 应用**：`backend/src/`、`frontend/src/`
- **移动端**：`api/src/`、`ios/src/` 或 `android/src/`
- 下方路径默认假设单项目；生成任务时必须根据 plan.md 中的结构调整

## 依赖与执行顺序

### 阶段依赖

- **准备（Phase 1）**：无依赖，可立即开始
- **基础能力（Phase 2）**：依赖准备阶段完成，阻塞所有用户故事
- **用户故事（Phase 3+）**：都依赖基础能力完成
  - 用户故事可在有人员时并行推进
  - 也可按优先级顺序推进（P1 → P2 → P3）
- **打磨（最终阶段）**：依赖目标用户故事完成

### 用户故事依赖

- **用户故事 1（P1）**：基础能力完成后即可开始，不依赖其他故事
- **用户故事 2（P2）**：基础能力完成后即可开始，可与 US1 集成但必须保持可独立测试
- **用户故事 3（P3）**：基础能力完成后即可开始，可与 US1/US2 集成但必须保持可独立测试

### 每个用户故事内部

- 如包含测试，测试必须先写并先失败，再实现
- 先模型，后服务
- 先服务，后端点
- 先核心实现，后集成
- 完成当前故事后再进入下一优先级

### 并行机会

- 所有标记 [P] 的准备任务可并行
- 所有标记 [P] 的基础任务可在 Phase 2 内并行
- 基础能力完成后，所有用户故事可按团队容量并行
- 同一用户故事中标记 [P] 的测试可并行
- 同一故事中的模型任务可并行
- 不同用户故事可由不同开发者并行推进

## 实施策略

### MVP 优先（仅用户故事 1）

1. 完成 Phase 1：准备
2. 完成 Phase 2：基础能力（关键，阻塞所有故事）
3. 完成 Phase 3：用户故事 1
4. **停止并验证**：独立测试用户故事 1
5. 准备好后部署或演示

### 增量交付

1. 完成准备 + 基础能力 → 基础就绪
2. 增加用户故事 1 → 独立测试 → 部署/演示（MVP）
3. 增加用户故事 2 → 独立测试 → 部署/演示
4. 增加用户故事 3 → 独立测试 → 部署/演示
5. 每个故事都在不破坏已有故事的前提下增加价值

### 并行团队策略

多人协作时：

1. 团队共同完成准备和基础能力
2. 基础能力完成后：
   - 开发者 A：用户故事 1
   - 开发者 B：用户故事 2
   - 开发者 C：用户故事 3
3. 各故事独立完成并集成

## 备注

- [P] 任务表示不同文件、无依赖
- [Story] 标签映射到具体用户故事，便于追踪
- 每个用户故事都必须可以独立完成和测试
- 实现前确认测试先失败
- 每个任务或逻辑分组完成后提交
- 可在任意检查点暂停并独立验证当前故事
- 避免：模糊任务、同文件冲突、破坏独立性的跨故事依赖
